# Add API rate limit dashboard for workspace admins

> Feature ID: `f9500f17-bb62-4a36-8324-d6dd88e97e85`

## Request

Support and engineering need to see which API keys or endpoints are hitting rate limits without digging through logs.

Build an admin page at /admin/rate-limits (admin role only) that shows:
- Table: client/API key label, endpoint pattern, current usage vs limit, window (e.g. per minute), last throttled at, throttle count (24h)
- Filters: all / throttled / healthy
- Empty state when no rate limits configured
- Use existing tRPC + Drizzle patterns; no new frameworks
- One API route test + one UI smoke test

Non-goals: editing limits in UI, billing, email alerts in v1.

Success: admin can spot a throttled client in under 30 seconds.

## Goals

- Enable workspace admins to view API rate limit status for all keys in under 30 seconds.
- Reduce the time spent troubleshooting API throttling issues by 50% within the first month of launch.
- Increase the number of API keys monitored by 100% by the end of Q1 2024.

## Acceptance Criteria

- [ ] Given the admin is on the /admin/rate-limits page, when the page loads, then a table of API keys and their rate limit status is displayed.
- [ ] Given the admin filters by 'throttled', when the filter is applied, then only throttled API keys are shown in the table.
- [ ] Given the admin filters by 'healthy', when the filter is applied, then only healthy API keys are shown in the table.
- [ ] Given there are no rate limits configured, when the admin visits the /admin/rate-limits page, then an empty state message is displayed.
- [ ] Given the admin clicks on an API key, when the details are displayed, then the current usage vs limit and throttle count are shown.
- [ ] Given the admin is on the /admin/rate-limits page, when they refresh the page, then the displayed data is updated to reflect the latest usage.

## Edge Cases

- If an API key has never been throttled, the throttle count should display as 0.
- If the API key usage exceeds the limit exactly at the time of the request, it should still be displayed as healthy until the next window.
- If the database is unreachable, the admin should see an error message instead of a blank page.
- If the admin applies a filter and there are no matching API keys, an appropriate message should be displayed.
